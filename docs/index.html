    Each change ends as clean, reviewed commits.

    This repo installs a Claude Code workflow. After each change that you ask for, Claude splits the work into logical commits. Then a fresh agent reviews those commits, fixes the problems, and amends the fixes into the commits. You get a branch that is ready to read.

    the problem

    Without a workflow, agent history is noisy.

    An agent writes code fast. The history it leaves is often hard to review and easy to learn wrong things from.

    One large commit

    A reviewer cannot read the change in steps. A revert removes everything, also the good parts.

    Fix on fix

    Each attempt stays in the history:

    • Retry failed uploads
    • Fix retry bug
    • Fix the fix

    Self-review agrees with itself

    The session that wrote the code reads its own reasoning again. It misses the same problems the second time.

    Later sessions read this history too. An agent that continues the branch sees the wrong attempt and its fixes, and it can copy the wrong attempt.

    rules/workflow.md

    The core loop runs after each change.

    The rule makes Claude commit and review each change automatically. You do not type the commands, and you cannot forget them.

    1. You

      Ask for a change

      A feature, a fix, a refactor. Any size.

    2. Claude

      Make the change

      The normal work in the main session.

    3. Claude · automatic

      /commit

      Split the work into logical, self-contained commits.

    4. Fresh context · automatic

      /cr --fix

      Review only the new commits. Fix each real finding. Amend the fixes.

    5. You

      Validate and push

      Read the report. Answer the open questions. Push when you agree.

    you main Claude session forked review context

    Scoped review

    The rule counts the new commits. If the branch holds earlier work, the review covers only the last N commits, not the whole branch again.

    No push

    Claude never pushes and never opens a pull request. You validate the change and push it.

    No empty runs

    If the work changes no file under version control, Claude skips both steps.

    skills/commit/SKILL.md

    Split the work by concern, not by file.

    A commit is a unit of review, of revert, and of history. A reviewer reads one idea at a time. After a rebase merge, each commit on main still holds one idea.

    • On the default branch, it creates a new branch first.

    skills/cr/SKILL.md

    A fresh agent reviews the commits and fixes them.

    The writer of the code is its weakest reviewer. A reader with no memory of the work reads the code as it is, not as it was meant to be.

    Main session wrote the code

    It knows the intent, the failed attempts, and the shortcuts it took. It reads its own code with those assumptions.

    Review context: fork

    It starts clean and reads only the diff and the repo. It looks for bugs, security problems, broken edge cases, and regressions.

    The fix bar

    The review fixes every finding that it is sure is real. It can leave a finding unfixed for one of three reasons only:

    DecisionA product, design, or naming choice for you.
    ScopeThe fix needs work outside the diff.
    RiskNo test, and the contract is unclear.

    "Minor" and "pre-existing" are not reasons to skip. Before the report, a re-triage pass checks each skipped item again.

    The report

    The review runs in its own context, so the report is the only thing that comes back. It always has six sections:

    1. Fixes applied, with the commit that carries each one
    2. Confirmed correct
    3. Needs your decision
    4. Deliberately not fixed
    5. Notes and open decisions
    6. Verification: the commands it ran

    If items 3 or 4 have entries, Claude asks you once which ones to fix.

    amend, don't append

    Each fix goes into the commit that needs it.

    The review amends a fix into the commit that introduced the problem. It adds a new commit only for an unrelated fix. The branch holds only commits that are already correct.

    For human reviewers

    Each commit is correct when you read it. You do not read a mistake in one commit and its fix three commits later.

    For a rebase merge

    The commits land on main as they are. Main gets a clean set of commits, with no fix chain.

    For agents

    A later session that continues the branch reads only correct code. It does not see a wrong attempt, so it cannot copy one.

    skills/cr-deep/SKILL.md · skills/cr-apply/SKILL.md

    Deep review: find in one session, apply in the next.

    /cr runs after each change. At the end of a non-trivial task, or at checkpoints in a large task, you run a much deeper review. It is slower and it finds more.

    /cr --fix/cr-deep + /cr-apply
    StartAutomatic, after each changeYou run it
    ReviewersOne agent in a forked contextSeveral agents in parallel, one for each angle
    DepthMedium, by defaultHigh, by default
    SpeedFastMuch slower
    OutputFixes, then a report in the chatA report file, then fixes in a separate session

    /cr-deep finds

    1. The orchestrator starts parallel reviewers, one for each angle:
      correctnesssecurityregressionsconventionsperformanceduplication
    2. It removes duplicates and ranks the findings by severity.
    3. It writes every finding to code-review-<branch>-<date>.md. The file stays untracked. By default, it changes no code.

    /cr-apply applies

    1. It creates a backup branch.
    2. It groups the findings by code area and runs the groups in sequence.
    3. Each group gets 1 to 5 agents. Parallel agents work in separate worktrees, on separate files.
    4. Each agent checks each finding against the current code before it fixes it.
    5. Each fix is a fixup! commit, folded with autosquash into the commit that introduced the defect.
    6. It writes a status for each finding into the report.

    Why two sessions: you can read the report before anything changes. A stopped run continues at the next open group. A finding that is wrong gets no fix.

    rules/

    Three rules load in every session.

    Claude Code loads each file in ~/.claude/rules/ in every project. They add to your own CLAUDE.md. They do not replace it.

    workflow.md

    Runs /commit and /cr --fix after each change. Never pushes.

    writing-style.md

    All prose is in Simplified Technical English (ASD-STE100): chat messages, plans, commit messages, PR text, and code comments.

    • Less ambiguity: one word, one meaning.
    • Faster human review of commits and reports.
    • No filler, no hedging.
    • Much less tiring to read agent output all day.

    skills/

    Three more skills.

    These support the workflow. You run each one when you need it.

    /ff-merge

    Lands a topic worktree on the feature branch it came from. It rebases the topic branch, then fast-forwards the feature branch. On a conflict, it stops and reports. It never makes a merge commit.

    /memory-cleanup

    Checks each auto-memory of the project against the repo. It repairs the index, merges duplicates, and removes stale entries. You confirm each change that loses information.

    /dotfiles-update

    Shows the new commits of this repo and the skills and rules that change. After you confirm, it updates the clone and runs install.sh.

    guardrails

    You stay in control of what leaves your machine.

    The skills rewrite local history. They never rewrite shared history.

    • No push, no pull requestNo skill pushes or opens a pull request. You validate and push.
    • No commits on the default branch/commit creates a branch first.
    • No rewrite of mainAmends and fixups target only commits after the merge base.
    • Backup before bulk fixes/cr-apply creates a backup branch, and prints the restore command at the end.
    • No shared stash/cr-apply and /ff-merge never use git stash. All worktrees share one stash stack.
    • Questions come to youDesign choices and risky fixes go into the report. Claude asks before it applies them.

    install.sh · update.sh

    Install with one script. Remove with one flag.

    The script links each item into ~/.claude. It does not copy files and does not change your CLAUDE.md.

    install, then start a new Claude Code session

    git clone https://github.com/einsteinx2/.dotfiles-claude.git ~/.dotfiles-claude
~/.dotfiles-claude/install.sh

    update

    /dotfiles-update                   # in Claude Code
~/.dotfiles-claude/update.sh       # in a terminal

    uninstall

    ~/.dotfiles-claude/install.sh --uninstall

    What the script does

    • It is idempotent. You can run it again at any time.
    • If you have an item with the same name, for example your own /commit, the script keeps your item and skips the item of this repo.
    • --force moves your item to ~/.claude/backups/dotfiles-claude/, then links the item of this repo.
    • It removes links to items that the repo no longer has.
    • It uses CLAUDE_CONFIG_DIR if you set it.
    • Keep the clone in place. The links point into it.

    Needs macOS or Linux, git, and bash. Details are in the README.
